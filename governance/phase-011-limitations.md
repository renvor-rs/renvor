## Security-relevant

| Row | What | Why it was not closed | Owner / target / consequence |
|---|---|---|---|
| **L-1** | **A generated starter speaks plaintext to Valkey, SMTP, and the OTLP receiver.** The development configuration the generator writes opts into plaintext explicitly (SR-005: a written double opt-in, never a URL scheme), the four full rows prove every capability against real plaintext loopback services, and no generated project has completed a TLS handshake with any of them. Inherits 010/L-1. | No trusted certificate authority exists on this machine or on a CI runner; a self-signed CA leg is CI work the generator cannot carry. | Maintainer; **Phase 012 CI leg with a self-signed CA**. Consequence: the TLS settings the templates render are compiled but never exercised end to end. |
| **L-2** | **Verification runs in a sealed environment that still inherits the caller's toolchain.** `renvor new` clears the environment before `fmt`, `clippy`, `build`, `test`, and the route-dump smoke and passes through an allow-list only (`PATH`, `HOME`, `USER`, `LOGNAME`, `TMPDIR`, `TEMP`, `TMP`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TERM`, and the `CARGO_HOME`/`RUSTUP_*` family), so no `RENVOR_*` test variable reaches the staged project — but the `cargo` that verifies is whichever one `PATH` resolves, and the starter ships no `rust-toolchain.toml`. | Pinning a toolchain in a generated project is a template-contract decision (C-4) the phase did not take; the framework's own MSRV is enforced by the gate on both toolchains, not by the generated tree. | `renvor-cli`; **Phase 012 (C-4 1.2.0)**. Consequence: a starter verified on one toolchain may fail its own `clippy -D warnings` on a newer one until the author pins it. |

## Correctness and operations

| Row | What | Why it was not closed | Owner / target / consequence |
|---|---|---|---|
| **L-3** | **The seeded lockfile is one package short.** The framework's `Cargo.lock` is copied into staging to seed resolution (FR-006, SR-007), and no workspace crate enables Tokio's `signal` feature, so the starter's first `cargo` invocation resolves `signal-hook-registry` against the registry index ("Locking 1 package", visible in every verification log). Generation itself still opens no socket; verification is `cargo`'s. | Adding a workspace edge only to widen the seed would put a dependency into the framework for the generator's convenience. | `renvor-cli`; **Phase 012** (a seed manifest beside the lock, or the edge once the facade needs it). Consequence: an offline first generation fails at verification unless the crate is already in the local registry cache. |
| **L-4** | **`renvor generate resource` knows five field types** — `string`, `text`, `integer`, `boolean`, `float` — and renders no relation, uniqueness, index, default, or nullable column. | The five cover the example domain and every generated test; relations need a decision on how the resource module names the other side. | `renvor-cli`; **Phase 012**. Consequence: anything else is a hand-written migration and repository, which the generator's rerun safety leaves untouched. |
| **L-5** | **Capabilities are chosen at `renvor new` and only there.** `renvor generate auth` adds the auth starter to a placed starter; there is no `renvor generate capability <name>`, so adding `cache`, `jobs`, `mail`, `storage`, or `observability` later is manual. | The auth generator exists because W-023's closure required a post-generation path; a capability generator has the same shape but was not in the phase's controls. | `renvor-cli`; **Phase 012**. Consequence: an author who wants a capability later regenerates into a scratch tree and merges by hand. |
| **L-6** | **`renvor generate auth` re-renders the affected starter files and reports every author-changed one as a conflict.** The resources block of `src/routes.rs` between the `// renvor:resources:begin/end` markers is carried across the re-render; every other differing file is a `generation_conflict` that writes nothing (FR-048, SR-009) and must be reconciled by hand. There is no three-way merge. | Merging arbitrary edits into a re-rendered file is not deterministic; refusing is the contract. | `renvor-cli`; **stays** (documented in the command reference). Consequence: adding auth late to a heavily edited starter is a manual merge. |
| **L-7** | **The generated `tests/starter.rs` drives the binary over a real loopback socket**, spawned as a child process — it needs a free port, a real database, and seconds of start-up per test — and cannot use the socket-free `renvor_testkit::app::TestApplication`, because what it proves is the binary's start-up order (database provider before pool-dependent routes), its signal handling, and its clean shutdown, which only a process has. | By design; `TestApplication` serves the framework's own end-to-end suite (`renvor-auth-http/tests/test_application.rs`) and any application test that builds its own `ApplicationBuilder`. | `renvor-testkit`; **stays**. Consequence: the generated test is an integration test, not a unit test; `cargo test` without `RENVOR_DATABASE_URL` prints `SKIPPED` and passes. |
| **L-8** | **The verification-mail confirmation in the generated test is skipped without a mail sink.** With `RENVOR_TEST_SMTP_API_URL` set the test reads the verification mail from Mailpit's API, confirms it, and asserts `email_verified: true`; without it the test prints `SKIPPED` for that step and passes. The four full rows run with the sink present, locally and in CI, so the flow is proven in the census and not in a bare environment. | A generated test cannot require a service its author may not run. | Template; **stays**, stated in the generated README. Consequence: an author without Mailpit sees the flow as skipped, not as proven. |
| **L-9** | **`rustfmt` is required at generation time for `renvor generate resource`.** Rendered Rust is formatted by the installed `rustfmt` before it is planned, so the resource files are byte-stable under `cargo fmt --check`; an absent `rustfmt` is `tool_missing`, and generation writes nothing. | Reproducing rustfmt's layout in a template is not achievable for every field list. | `renvor-cli`; **stays** (documented in C-4 1.1.0). Consequence: the resource generator has one more tool prerequisite than `renvor new`. |
| **L-10** | **No database-backed starter row runs on Windows, and no generated test asserts a clean shutdown there.** The four full rows, the six lean rows, the four generator rows, and the parity proof are proven on macOS (this machine) and on `ubuntu-latest` (the CI `verify` job); the platform job runs `RENVOR_TEST_STARTER_ROWS=nodb` only. On Windows a test cannot send its child the interrupt a terminal sends, so the generated test ends the process and prints `SKIPPED` for the clean-exit assertion instead of faking one (PR #62's Windows legs found the assertion unconditional). | The platform job has no database, Valkey, or Mailpit containers; Windows refuses loopback connections slowly (recorded in Phase 010); a console control event is not a signal. | CI and the templates; **Phase 012**. Consequence: a Windows-only regression in a generated starter's database path or shutdown path would surface only when an author runs it. |
| **L-11** | **Template metadata is recorded; nothing upgrades a project with it.** `.renvor/generated.toml` records the generator version, the template version, and a SHA-256 per generated file (SR-008: digests, never contents), and every `generate` command uses it to tell unchanged, regenerated, and conflicting files apart. There is no `renvor upgrade`, and drift in a generated file is noticed only when a `generate` command plans that path. | The record is the prerequisite; an upgrade command needs a template-diff policy that C-4 1.1.0 does not yet state. | `renvor-cli`; **Phase 012**. Consequence: upgrading a placed project across template versions is regenerate-and-diff by hand. |
| **L-12** | **The census's negative controls are run by hand.** `cargo xtask census` fails when a row's test does not report (a renamed, deleted, or `cfg`-gated starter row), and that is proven by three controls run from a scratch script and quoted in the evidence — not by a test that mutates the row table itself. | A test that renames a test in its own binary is not expressible without a second build. | `xtask`; **stays** (the controls are re-run and re-recorded each phase). Consequence: the proof that the census notices a vanished row is evidence, not CI. |
| **L-13** | **`renvor-auth` is in every database-backed starter's runtime graph, chosen or not.** Both persistence adapters (`renvor-sqlx`, `renvor-seaorm`) implement the auth repositories and depend on `renvor-auth` unconditionally, so a starter with a database and `--auth none` still links the auth domain crate; only `renvor-auth-http` — the routes — follows the choice. Found by FR-024's lock-closure walk (`lock_closure` in `starter_matrix.rs`, which asserts exactly this shape); the capability crates are absent when unselected. | Making the adapters' auth repositories optional is a feature split across two adapters and the testkit's shared suite — Phase 012 work with its own record. | `renvor-sqlx`, `renvor-seaorm`; **Phase 012**. Consequence: a database starter without auth compiles `renvor-auth` (no route, no endpoint, no migration of its own). |
| **L-14** | **The rename-failure branch of the transactional commit is reached by no test.** `apply::commit` stages every file as a temporary sibling, then renames each into place; a failure while renaming rolls back what was placed. A rename after a successful stage in the same directory fails only on a cross-device move, which a test cannot arrange on one filesystem, so the branch is covered by a direct test of the rollback function it calls and by the injected failure beside it (`RENVOR_FAIL_AT=generate-commit`), not by a real rename failure. Found by mutation M-G15's first form. | Simulating the failure would need a filesystem boundary inside the project, or a seam in production code that exists only for the test. | `renvor-cli`; **Phase 012** (a cross-device fixture in CI, if one is worth it). Consequence: a defect in that one branch's bookkeeping would surface only on an actual cross-device rename. |
| **L-15** | **Reserved SQL identifiers are refused from a curated list, not from the engines.** `renvor generate resource` refuses a type name or a field that would be a bare keyword on PostgreSQL or MySQL 8.4 from a sorted table in `generate.rs` (the union of the two documented reserved lists). A keyword outside that table — a future engine version's, or one of the two lists' non-reserved-but-troublesome words — would still be accepted and fail at the project's first query, exactly the failure the Codex review described. The generated SQL keeps identifiers unquoted, so quoting was not taken as the fix (it would make every generated statement engine-specific). | The engines publish their reserved lists as documentation, not as an API the generator could ask. | `renvor-cli`; **Phase 012**: a test that asks each live engine `SELECT 1 AS <word>` for every word the table does not hold, from the engines' own keyword tables (`pg_get_keywords()`, `INFORMATION_SCHEMA.KEYWORDS`). Consequence: an unlisted keyword is a first-query failure rather than a refusal at generation. |
| **L-16** | **A starter's rendered Rust is not passed through `rustfmt`, so the project's name can decide whether verification passes.** `renvor generate resource` formats its rendered module with the toolchain's `rustfmt` before planning, because user-named types decide line widths (FR-045); `renvor new` renders the starter and then runs `cargo fmt --check` on it. A name long enough to push a rendered line past rustfmt's width rules therefore fails generation with `project_verification_failed` ("a defect in renvor's templates"). Measured on 2026-09-05: the correction round's new census row is named `authaddedmysql` (14 characters), and its `config.rs` test line `assert_eq!(defaults["local_domain"].as_str(), Some("authaddedmysql.test"))` crossed rustfmt's call width where every earlier row's name (at most 11 characters) had not. That site is now width-independent, and the same run found a second, name-independent layout defect in the SeaORM repository template's `create` signature without auth — a combination no earlier row rendered. | Formatting every rendered file in staging is a change to what `renvor new` writes, beyond the review's findings; the round fixed the sites it measured. | `renvor-cli`; **Phase 012**: run `rustfmt` over the staged starter's Rust files before verification, as the resource generator does, and add a long-name row. Consequence: a project name that reaches an unfixed width-dependent site fails generation with a message that blames the templates — correctly, but not usefully to the operator. |
