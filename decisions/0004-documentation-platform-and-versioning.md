## Context

Renvor needs a documentation site before it has documentation, because the *verification
sequence* includes building and link-checking that site (steps 8 and 9). A framework whose
documentation build is added later is a framework whose documentation is unverified for
however long "later" takes.

Constraints that shaped the choice:

1. **Prose and generated API reference must describe the same contract at the same
   version** (FR-056). Two sources of truth that can disagree about the MSRV is a defect
   waiting to be reported as a bug.
2. **Search must not depend on a hosted third-party index** (FR-054). A hosted search
   service is a runtime dependency on someone else's infrastructure, sends reader queries
   to a third party, and stops working offline.
3. **Broken links must fail the build**, not warn. A warning in a build log is not a gate.
4. The project already accepts a Node toolchain cost for nothing else. Whatever is chosen,
   that cost must be justified rather than absorbed silently.

## Decision

The documentation site is **Docusaurus 3.10.2**, in `docs/`, with:

- **`@easyops-cn/docusaurus-search-local`** providing a search index built at compile time
  and shipped with the site. Search works offline and no query leaves the reader's browser.
- **`onBrokenLinks: 'throw'`**, `onBrokenAnchors: 'throw'`, and
  `markdown.hooks.onBrokenMarkdownLinks: 'throw'` — a broken link fails the build.
- **No blog.** The project has nothing to announce; an empty blog is a maintenance surface
  with no reader.
- **An explicit sidebar**, not autogenerated, so adding a file cannot silently change
  published navigation.
- **`.nvmrc` pinning the Node 22 LTS line**, referenced by both contributors and CI.
- **`docs/package-lock.json` committed**, per the lockfile rule for applications and
  documentation sites.

### Version stamping

A single MDX partial, `docs/docs/_stamp.mdx`, carries the crate version, the MSRV, and the
documentation-set version. **Every prose page and the API reference page import that same
partial.** There is exactly one value, so prose and API documentation cannot drift into
describing different versions — not by discipline, but by construction (FR-056).

Updating the crate version without updating the stamp is a defect, not a formatting detail.

### Versioning cadence

Docusaurus versioned docs are **not** enabled yet. While the project is pre-`0.1.0` there
is one supported version and snapshotting would create archives of documentation for
software that never shipped. Versioning is introduced at the first `0.1.0` release, and the
cadence then follows the release cadence: one documentation version per minor release.

## Alternatives considered

| Alternative | Rejected because |
|---|---|
| **mdBook** | The natural Rust-ecosystem choice and it avoids Node entirely, which is a real advantage. Rejected because its built-in search is weaker, it has no first-class versioning story, and mixing rustdoc output with prose requires custom tooling the project would then own and maintain. |
| **MkDocs + Material** | Excellent search and mature versioning via `mike`. Rejected because it trades a Node toolchain for a Python one — the cost is moved, not removed — and the project has no other Python dependency, whereas Node is already required by nothing and would be required by any JS-based alternative anyway. |
| **Zola** | Single static binary, no runtime toolchain at all, and fast. Rejected because documentation-site features (versioned docs, sidebar generation, MDX components) would all be hand-built, and the version stamp mechanism above would become bespoke code to maintain. |
| **Docusaurus with Algolia DocSearch** | The default and best-in-class hosted search. Rejected explicitly by FR-054: it is a third-party runtime dependency, sends reader queries off-site, requires an application and approval process, and breaks offline. |
| **No documentation site in Phase 001** | Would leave verification steps 8 and 9 unexercised, meaning the documentation build is unverified until someone adds it — and the ordering defect this ADR was written alongside proves how easily that slips. |

## Consequences

**Accepted costs — stated, not absorbed silently:**

- **A Node toolchain is now required** to run the full verification sequence. Contributors
  who only touch Rust must still install Node and npm, or `cargo xtask verify` exits 2.
  This is the single largest cost of this decision.
- **1,320 npm packages** enter the dependency graph for the documentation site. They are
  covered by Dependabot's `npm` ecosystem and the committed lockfile, but the supply-chain
  surface is real and is not covered by `cargo deny`.
- **Docusaurus major upgrades are migrations**, not bumps.
- **Three lychee exclusions** exist while the site is undeployed and the crate unpublished;
  each carries a removal condition in `lychee.toml` and must be removed when it expires.

**What is locked in:** the published documentation URL structure, once `renvor.dev` serves
the site.

**To reverse this**, a superseding ADR must address the published URL structure and provide
redirects for any indexed page.
